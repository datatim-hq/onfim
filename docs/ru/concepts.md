# Основные понятия

[English](../concepts.md) · **Русский**

Здесь описано, как Onfim устроен как память: что такое запись, как она набирает и теряет силу, как новое утверждение
заменяет старое, что делают ночной и еженедельный «сон» и как решается доступ. Справочники REST и MCP
([rest-api.md](rest-api.md), [mcp.md](mcp.md)) описывают те же операции по вызовам.

Подробная версия этой страницы — спецификации в [`docs/ru/design/`](design/README.md), главная из них —
`05-lifecycle.md`.

## Сервис не переписывает то, что прислал клиент

На пути записи у Onfim нет LLM. Что запомнить, как сформулировать и к какому виду отнести, решает клиент (ваш агент).
Сервис сохраняет `text`, `kind`, `subject`, `slot`, `tags`, `importance` и доказательства в том виде, в каком они
пришли. Дальше он меняет у записи только **состояние** (текущая, претендент, заменённая, в архиве) и **силу** — и
только по правилам, описанным ниже. Если факт изменился, пишется новая запись, а старая уходит в историю.

При записи стоит знать о двух вещах:

- **Скрытые символы вырезаются.** Из `text` и `quote` удаляются символы нулевой ширины и другие невидимые символы,
  управляющие символы направления текста, теговые символы Unicode, ANSI-последовательности и управляющие символы. Что
  удалено, записывается во `flags` записи (например, `removed:invisible:U+200B`). Слова из смешанных алфавитов и
  читаемый текст в base64/hex только помечаются (`flag:mixed-script:...`, `flag:encoded:base64`) и не меняются.
- **Секреты не принимаются.** Текст или цитата, похожие на закрытый ключ или токен API (Anthropic, OpenAI, GitHub,
  GitLab, AWS, Google, Slack, Stripe, бот Telegram, JWT), отклоняются с `400`. Ключам в памяти не место.

## Записи

У записи («воспоминания») есть:

| Поле | Значение |
|---|---|
| `text` | сам факт, до 4000 символов |
| `kind` | вид факта (см. ниже); обязателен, сервис его никогда не меняет |
| `subject` | о чём факт, в свободной форме: `project:shop`, `person:bob`, `crm:deal:42` |
| `slot` | «какой признак субъекта»: `project:shop#deploy_process`, `person:bob#role`. В слоте не больше одной текущей записи |
| `tags` | список строк; фильтры в поиске действительно фильтруют |
| `importance` | 1, 2 (по умолчанию) или 3; разовая оценка клиента, задаёт начальную силу |
| `visibility` | где факт можно *произносить*: `shareable` (по умолчанию), `same_chat`, `owner_only` |
| `classification` | кто может его *читать*: 0 — открыто, 1 — для внутреннего пользования, 2 — конфиденциально, 3 — строго ограничено |
| `occurred_at` | когда факт стал верным или событие произошло (необязательно) |
| `external_ref` | собственный id клиента; повторная запись с тем же `external_ref` добавляет доказательство, а не новую запись |
| `evidence` | хотя бы один источник (следующий раздел) |

Сервис добавляет `id`, `state`, `strength`, `evidence_count`, `trust`, `flags`, `valid_from`/`valid_to`, `source`
(id клиента, который сделал запись), `pinned` и связи вроде `supersedes_id`, `duplicate_of` и `promoted_from`.

### Виды и профили

У каждого пространства есть **профиль**, который определяет, какие виды оно принимает. От вида зависит, как запись
затухает, можно ли её забыть и какой у неё вес в ранжировании.

| Вид | Профили | Период полураспада | Забывается по силе | Вес в ранжировании |
|---|---|---|---|---|
| `decision` — принятое решение | work, team | нет | нет | 1,0 |
| `convention` — соглашение кода или проекта | work, team | нет | нет | 0,9 |
| `gotcha` — грабля и её обход | work | 180 дней | нет; при силе ниже 0,25 еженедельный сон спрашивает «ещё актуально?» | 0,9 |
| `note` — всё остальное | work | 90 дней | да | 0,5 |
| `insight` — вывод (в том числе сводки глубокого сна) | work, assistant, team | 120 дней | да | 0,7 |
| `person_fact` — факт о человеке | assistant, team | 365 дней | да | 0,9 |
| `topic_fact` — контекст чата, темы или проекта | assistant, team | 180 дней | да | 0,8 |
| `episode` — итог дня в чате | assistant, team | 30 дней | да | 0,4 |
| `feedback` — поправка владельца к работе агента | assistant | 180 дней | да | 0,8 |
| `commitment_mirror` — зеркало обязательства, которое ведётся в другой системе | assistant, team | не затухает, пока открыто; 14 дней после `close` | да | 1,0 |
| `crm_mirror` — зеркало сущности CRM | assistant, team | не затухает, пока открыто; 14 дней после `close` | да | 1,0 |

- **work** — память разработки для ассистентов программиста (Claude Code, Cursor и подобных).
- **assistant** — память личного ассистента о людях, чатах и обязательствах.
- **team** — общий слой команды.

Запись вида, который профиль пространства не разрешает, возвращает `400`. Виды хранятся в таблице `kinds` и меняются
только миграцией.

## Доказательства

У каждой записи должно быть хотя бы одно доказательство — откуда взят факт. Запись без доказательства отклоняется
(`400`).

```json
{
  "source_ref": "claude-code:shop",
  "source_scope": "dev",
  "observed_at": "2026-10-09T12:00:00Z",
  "speaker": "agent",
  "quote": "redirects behind the proxy go to localhost"
}
```

| Поле | Обязательно | Значение |
|---|---|---|
| `source_ref` | да | указатель на источник: URL, id сообщения, `claude-code:<project>` |
| `source_scope` | да | тип места, откуда пришёл факт: `dev`, `owner`, `web`, `chat:<id>`, ... |
| `observed_at` | да | время наблюдения в ISO 8601 |
| `speaker` | нет | кто это сказал: `owner`, `agent`, `person:bob` |
| `quote` | нет | короткая дословная цитата, до 200 символов |
| `speaker_principal` | нет | id человека из организации, который это сказал (память команды) |
| `forwarded_from` | нет | исходный автор пересланного сообщения |
| `independent_key` | нет | переопределяет, как считается независимость (для опытных) |

Зачем это нужно:

- **Объяснимость.** Результаты поиска, отчёты сна и очередь решений показывают, кто что сказал и когда, поэтому агент
  может ответить «по словам Боба, 22 сентября», а человек — рассудить спор.
- **Сила.** Факт становится сильным именно от подтверждений из независимых источников (следующий раздел).
- **Доверие.** Доверенная запись или нет, вычисляется по её доказательствам, а не по тексту (см. [Доверие](#trust)).

**Независимость.** Два доказательства независимы, если различаются их ключи независимости. По умолчанию ключ — это
`p:<speaker_principal>`, если назван человек, `fwd:<forwarded_from>` для пересланных сообщений, иначе
`<speaker>@<source_scope>`. Доказательства с почти одинаковыми цитатами (один и тот же текст от 12 символов или три
общих фрагмента по 32 символа) никогда не считаются независимыми: пересылка или копипаста — это один источник. Второе
доказательство с тем же `source_ref` у той же записи игнорируется.

<a id="strength-and-decay"></a>

## Сила и затухание

Сила `s` — число из [0, 1]: насколько знание живо. Это не то же, что `importance`, которую клиент задаёт один раз.

**Начальная сила:** 0,35 / 0,55 / 0,75 для важности 1 / 2 / 3, плюс 0,10, если первое доказательство — от владельца
личного пространства (`speaker: "owner"`), но не больше 0,90. Дополнительные доказательства в той же записи её
подкрепляют.

**Подкрепление:** каждое событие сдвигает силу к 1, не перескакивая: `s ← s + w·(1 − s)`.

| Событие | w |
|---|---|
| Новое независимое доказательство | 0,30 |
| Доказательство из уже известного источника | 0,05 |
| Подтверждение владельца (`confirm` или принятый пункт очереди) | 0,50 |
| `used` — запись использована в ответе или работе | 0,15 |
| `helpful` — запись оказалась полезной | 0,25 |
| Запись попала в первые 5 результатов поиска (не чаще раза в сутки) | 0,03 |
| Эпизод вошёл в сводку глубокого сна | `s ← s · 0,5` |

**Затухание:** `s(t) = s(t₀) · 2^(−Δдней / период полураспада)`. Затухание считается при чтении и записывается ночным
сном; пересчёт никогда не повышает силу. Закреплённые записи, виды без периода полураспада и открытые зеркала не
затухают.

Поиск ранжирует по фиксированной формуле, где смешаны релевантность и сила:

```
score = 0.50·sem + 0.20·lex + 0.20·strength + 0.10·prior
```

- `sem` — векторное сходство, нормированное min-max среди кандидатов;
- `lex` — ранг полнотекстового поиска (Postgres, english и russian), нормированный; 0 без совпадения;
- `prior` — вес вида в ранжировании × importance / 3.

Кандидаты — первые 50 по вектору и первые 50 по полному тексту, после всех фильтров. При равенстве выше идёт более
новая запись, затем — по id, поэтому один и тот же запрос на тех же данных всегда даёт один и тот же порядок.
`explain=true` возвращает слагаемые.

## Слоты, претенденты и замена

В слоте не больше одной **текущей** записи. Новое утверждение заменяет старое, только когда оно подтверждено.

**Явная замена.** Клиент передаёт `supersedes: <id>` текущей записи. В одной транзакции старая запись становится
`superseded` (с `valid_to`), а новая — `current`. Ответственность берёт на себя клиент.

**Через слот.** Новая запись в занятом слоте без `supersedes` становится **претендентом**; текущая запись остаётся в
силе. В ответе есть `slot_current_id`. Каждую ночь лёгкий сон проверяет шлюз **G1**: претендент заменяет текущую запись,
только если выполнено всё:

1. претендент не старше текущей записи (`occurred_at`, иначе `created_at`);
2. он подтверждён: доказательством от владельца, или хотя бы двумя независимыми доказательствами, или тот же человек,
   который дал первое доказательство текущей записи, передумал;
3. после первого доказательства претендента к текущей записи не пришло новых доказательств.

Пока претендент ждёт, поиск возвращает текущую запись с `contested: true` и id претендента.

- Если претендент не прошёл G1 за **14 дней**, в очередь решений уходит пункт `contradiction` с цитатами обеих сторон.
- Если решения нет и через **30 дней**, претендент уходит в архив, а пункт истекает.
- Опоздавшее утверждение (старше текущей записи) сразу уходит в историю как `superseded`.
- **Повтор того же утверждения** (тот же вид, субъект, видимость и классификация, тот же текст без учёта регистра,
  лишних пробелов и точки в конце) в слот, где текущая запись говорит ровно это, считается подтверждением:
  доказательство добавляется к текущей записи, в ответе `reinforced: true`. Это не действует для видов-правил, явного
  `supersedes`, записей с `external_ref` и когда в слоте уже ждёт претендент.

**Откат.** `revert-supersede` в течение 30 дней возвращает старую запись в `current`, а новую — в `candidate`.
`history` показывает все версии слота (или цепочки замен) с `valid_from`/`valid_to` и переходами.

Записи без слота механически не сравнить; еженедельный глубокий сон может *предложить* для них расхождение или слот,
но сам ничего не заменяет.

<a id="the-review-queue"></a>

## Очередь решений

Спорное и неясное уходит к человеку. Пункты создают сон и некоторые записи:

| Тип | Когда создаётся | Принять | Отклонить |
|---|---|---|---|
| `contradiction` | претендент ждал 14 дней или глубокий сон нашёл противоречие | передайте `winner`; остальные заменяются, победитель получает подтверждение владельца | ничего не меняется |
| `slot_suggestion` | глубокий сон считает, что записи описывают один признак | слот проставляется; самая новая запись становится текущей, более старые заменяются | ничего не меняется |
| `stale` | сила `gotcha` упала ниже 0,25 | запись уходит в архив | «ещё актуально» — считается подтверждением владельца |
| `merge_suggestion` | сводка глубокого сна не прошла шлюз G2 | сводка записывается как `insight`; источники теряют половину силы | ничего не меняется |
| `rule_confirm` | правило (`decision`, `convention`, `gotcha`) пришло из недоверенного источника или от не-куратора в слое команды | правило становится текущим (заменяя текущую запись слота, если она есть) | претендент уходит в архив |
| `promotion` | кто-то предложил перенести запись в этот слой | здесь создаётся новая запись | ничего не создаётся |

Для решения нужно право `review`. Агенты должны решать только по прямому слову человека. Открытые пункты истекают
через 30 дней.

## Забывание

**Шлюз G3** (лёгкий сон) отправляет текущую запись в архив, когда выполнено всё: её вид забываемый, она не закреплена,
её сила ниже **0,08**, за 30 дней у неё не было событий `used`/`helpful` и она не входит в открытый пункт очереди по
своему слоту. Архив обратим: `unarchive` возвращает запись с силой 0,30.

Историей занимаются правила хранения (таблица `retention_rules`): по умолчанию заменённые записи старше 180 дней уходят
в архив, а записи в архиве старше 365 дней удаляются — в пространстве, id которого буквально `assistant`.

Явное забывание: отправить в архив или удалить одну запись, либо `forget` по фильтру. Массовому `forget` всегда нужен
фильтр, по умолчанию он работает как пробный прогон и применяется только с `dry_run: false` и `confirm`, равным числу
найденных записей. Удаление настоящее: запись, её доказательства, события и вектор исчезают; журнал аудита хранит
только id.

<a id="sleep"></a>

## Сон

Сон выполняется в контейнере `worker` (см. [operations.md](operations.md#the-worker-and-the-sleep-schedule)). Каждая
стадия идёт в своей транзакции; пробный прогон откатывает все стадии и возвращает те же счётчики. Повторный запуск на
тех же данных ничего не меняет.

**Лёгкий сон** — каждую ночь, детерминированный, без модели:

| Стадия | Что делает |
|---|---|
| `decay` | записывает затухшую силу |
| `dedup_exact` | сливает точные дубли (то же пространство, вид, субъект, классификация, видимость, слот и нормализованный текст); доказательства переходят к оставленной записи, дубль скрывается с `duplicate_of`. Записи `same_chat` сливаются, только если их чаты совпадают |
| `promote` | шлюз G1 для всех претендентов; через 14 дней создаёт пункты `contradiction`, через 30 отправляет претендентов в архив |
| `forget` | шлюз G3 |
| `retention` | правила хранения; удаляет личные слои ушедших людей, когда наступает их дата |
| `review_expiry` | закрывает как истёкшие пункты очереди, открытые дольше 30 дней |
| `maintenance` | проверяет инварианты (одна текущая запись на слот, у каждой заменённой записи есть `valid_to`, у каждой записи есть доказательство, сила в [0, 1]) |
| `export` | пишет файл JSONL на каждое пространство, если задан `MEM_EXPORT_DIR`, и хранит 14 последних |

**Глубокий сон** — раз в неделю, при желании с LLM. Модель только предлагает; ничего из сказанного ею не применяется
без детерминированной проверки:

| Стадия | Что делает | Результат |
|---|---|---|
| `contradictions` | по каждому субъекту просит у модели пары записей, которые не могут быть верны одновременно | пункты `contradiction` |
| `slot_suggestions` | просит группы записей без слота, которые описывают один меняющийся признак (не для эпизодов, зеркал, выводов) | пункты `slot_suggestion` |
| `stale` | детерминированно: записи `gotcha` с силой ниже 0,25 | пункты `stale` |
| `summaries` | эпизоды одного субъекта старше 30 дней, сгруппированные по месяцам, сводятся в сводку | применяется автоматически, если прошёл шлюз **G2**, иначе — пункт `merge_suggestion` |

**Шлюз G2** принимает сводку, только если каждая дата, время и число в ней есть в источниках, каждое имя собственное
есть в источниках, она не длиннее источников, все источники — эпизоды и она на том же языке, что источники. Принятая
сводка — новая запись `insight` (`source: sleep:deep`), её доказательства — объединение доказательств источников;
источники остаются, но их сила уменьшается вдвое.

Что видит модель: тексты и цитаты одного субъекта в одном пространстве за раз. Записи с `classification` 3 или
`visibility: owner_only` не отправляются никогда. Модели по умолчанию нет: без `MEM_DEEP_MODEL_*` стадии с моделью
получают статус `DISABLED`, и выполняется только детерминированная стадия `stale`.

**Честный статус.** Прогон `OK`, только если все стадии прошли успешно. Ошибка в `decay`, `promote`, `forget`,
`retention` или `maintenance` делает лёгкий сон `FAILED`; ошибка в любой другой стадии (и в любой стадии глубокого сна) —
`PARTIAL`. Всё, кроме `OK`, отправляет оповещение. Стадия, отключённая оператором, получает статус `DISABLED`.

**Отчёт сна** (`sleep/latest`) показывает по каждому пространству: что заменено (оба текста, причина и цитаты), что
забыто (число по видам и до 10 примеров), слитые дубли, истёкших претендентов, открытые расхождения, а для глубокого сна
ещё предложения слотов, пункты «протухло?» и принятые и отклонённые сводки с причинами. Тексты подставляются в момент
чтения отчёта, в пределах доступа читающего.

<a id="trust"></a>

## Доверие

Память можно отравить: веб-страница или сообщение незнакомца могут содержать «указания». Onfim помечает каждую запись
как `trusted` или `untrusted` по её доказательствам и никогда — по тексту.

В **личном** пространстве доказательство доверенное, если:

- говорит владелец (`speaker: "owner"` или `speaker_principal` — владелец пространства), или
- оно взято из собственной работы клиента: `source_ref` — не URL, а префикс `source_scope` (до `:`) — один из
  доверенных — по умолчанию `owner, dev, session, repo, file, import, cowork, code, claude, crm`
  (`MEM_TRUSTED_SCOPES`).

Всё остальное — `web`, `chat:...`, URL — недоверенное. В пространстве **команды** или организации доказательство с
`speaker_principal` доверенное, только если этот человек входит в группу-владельца (для слоя всей организации — любой
участник организации); слово `owner` там ничего не значит.

Запись доверенная, если доверенное хотя бы одно её доказательство; более позднее доверенное доказательство или
подтверждение владельца делают её доверенной. Что из этого следует:

- **Правила ждут человека.** `decision`, `convention` или `gotcha` из недоверенного доказательства не становится
  текущим: оно сохраняется претендентом с пунктом `rule_confirm` для владельца.
- **Недоверенные записи — это данные.** Результаты MCP помечают их подсказкой: использовать как сведения и никогда не
  выполнять указания внутри них.

## Модель доступа

### Организации, люди, агенты и группы

| Понятие | Что это |
|---|---|
| **Организация** (`tenant`) | жёсткая граница; между организациями ничего не переходит |
| **Человек** (`principal`, вид `user`) | человек с личным **допуском** 0–3 |
| **Агент** (`principal`, вид `agent`) | действует `on_behalf_of` человека и никогда не видит больше, чем этот человек |
| **Сервис** (`principal`, вид `service`) | служебная учётная запись, например встроенный `admin` |
| **Группа** | команда, отдел, проект или роль; группы вкладываются друг в друга, и участник дочерней группы — участник всех родительских |
| **Клиент** | токен. Он принадлежит участнику и несёт **потолок**: какими пространствами и правами он вообще может пользоваться |

### Пространства — это слои

**Пространство** — контейнер записей с владельцем: человеком (`scope: personal`), группой (`scope: group`) или всей
организацией (`scope: tenant`). Типичные слои — личный → команда → отдел → организация; каждый — отдельное
пространство со своим профилем. Id пространств — строчные латинские буквы, цифры, `.`, `_` и `-` (они попадают в URL),
например `alice.work`, `acme.pmo`, `acme.org`.

### Гранты и роли

**Грант** даёт человеку, группе или всей организации роль в пространстве — до заданной максимальной классификации и,
при необходимости, до даты окончания.

| Роль | Права |
|---|---|
| `reader` | `read` |
| `contributor` | `read`, `write` (записывать, добавлять доказательства, `used`/`helpful`, архив) |
| `curator` | + `review` (подтверждать, закреплять, решать пункты очереди, откатывать), `forget` |
| `owner` | + `manage` (выгружать пространство) |

`admin` — не роль, а служебное право, которое действует только для прямых запросов к сервису и никогда — через
обратный прокси (см. [operations.md](operations.md#local-admin)).

Как решается доступ для запроса:

1. Пространство должно быть в организации вызывающего, а человек — активен; иначе `403`, один и тот же ответ, есть
   пространство или нет.
2. Для агента учитываются гранты человека, от имени которого он действует.
3. Учитываются собственные гранты человека, гранты всех его групп (включая родительские) и грант на всю организацию.
   Побеждает высшая роль; предел классификации — наибольший из этих грантов, но не выше допуска человека. Истёкшие
   гранты не учитываются.
4. Потолок токена урезает результат: действующие права = права роли ∩ права токена, а пространство должно быть в списке
   токена (или список — `*`).

Роль участника группы (`member`/`curator` в `add-member`) хранится, но сама по себе ничего не даёт; права в
пространстве дают только гранты.

### Классификация

У каждой записи уровень 0–3. Новая запись получает уровень пространства по умолчанию (при необходимости понижается до
предела пишущего); запись выше своего предела — `400`. Записи выше предела вызывающего для него не существуют: их нет в
поиске, списках, счётчиках, истории и отчётах, а прямой `GET` возвращает `404`. Чтение записей уровня 2 и выше пишется
в `access_log` (только id).

`visibility` — другая ось: где факт можно повторять. С `audience: "chat:<id>"` в поиске возвращаются записи
`shareable`, записи `same_chat` — только если какое-то доказательство пришло из этого чата (часть после `:` в
`source_scope`, например `chat:123`), а `owner_only` — никогда.

### Изоляция в базе

Сервис подключается под ролью без права обходить защиту на уровне строк (RLS). Каждый запрос задаёт список
пространств, которые ему можно трогать, а политики Postgres скрывают все остальные строки, поэтому ошибка в запросе не
может открыть чужое пространство.

### Память команды

- **Делегированные клиенты.** Агент команды может работать с токеном `--delegate-group`. В каждом запросе он должен
  сказать, от чьего имени действует, заголовком `X-Mem-On-Behalf-Of: <person>` или
  `X-Mem-On-Behalf-Of: group:<group>` (нет заголовка — `400`; человек не из группы — `403`). При действии от имени
  группы учитываются только гранты группы, поэтому личные слои недоступны по построению. Делегированные клиенты
  работают только через REST.
- **Правила в слое команды.** `decision` или `convention` в пространстве команды сразу становится текущим, только если
  это сказал человек с правом `review` там (куратор); иначе правило ждёт претендентом с пунктом `rule_confirm`.
- **Перенос между слоями.** `POST .../memories/{id}/promote` предлагает копию текущей записи в другое пространство той
  же организации (нужно `write` в обоих). Куратор целевого пространства принимает или отклоняет её в очереди решений;
  исходная запись не меняется. Классификация никогда не понижается. Виды, перечисленные в настройке `promotion_auto`
  целевого пространства, принимаются без проверки.
- **Псевдонимы субъектов.** `POST .../aliases` связывает один субъект с другим для всей организации (например,
  `person:tg123` → `crm:contact:77`); фильтр по `subject` учитывает псевдонимы в обе стороны.
- **Уход человека.** `offboard` деактивирует человека и его агентов, удаляет их токены, убирает человека из групп и
  назначает удаление его личных пространств (по умолчанию через 30 дней). Его цитаты в памяти команды остаются как
  доказательства.
- **Забыть субъект.** `forget-subject` удаляет все записи о субъекте и его псевдонимах во всей организации, с пробным
  прогоном и подтверждением числа.
