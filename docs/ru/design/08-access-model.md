# 08. Модель доступа: организации, пользователи, группы и слои памяти

[English](../../design/08-access-model.md) · **Русский**

> v0.3, 24.09.2026. Цель — заложить в архитектуру корпоративную память, пока пользователь один. Сейчас всё работает в одной «организации» владельца, но данные и проверки уже устроены так, что добавить компанию, отделы и сотрудников — это данные и гранты, а не переделка кода.

## Назначение

В корпоративной памяти разные люди видят разное: сотрудник — свою личную память, память своей команды и общую память компании; руководитель отдела — ещё и память отдела; финансовые и кадровые сведения — только те, кому положено. Агенты (Claude Code, Cowork, бот) работают **от имени человека** и никогда не видят больше, чем он.

## Понятия

| Понятие | Что это | Пример |
|---|---|---|
| **Организация** (`tenant`) | Жёсткая граница. Данные разных организаций не пересекаются ни в поиске, ни во сне, ни в выгрузке | `demo` (личная), позже `acme` |
| **Участник** (`principal`) | Кто обращается к памяти: `user` — человек; `agent` — агент от имени человека (`on_behalf_of`); `service` — служебный процесс (импорт, сон) | `alice`; `claude-code` → от имени `alice` |
| **Группа** (`group`) | Команда, отдел, роль, проектная группа; группы вложены (дерево). Член дочерней группы — член всех родительских | `acme` → `acme/pmo` → `acme/pmo/shop-team` |
| **Слой памяти** = **пространство** (`namespace`) | Контейнер записей с владельцем: человек (`personal`), группа (`group`) или вся организация (`tenant`). Id — через точку (входит в URL) | `work` (личное alice), `acme.pmo`, `acme.org` |
| **Грант** | Кто (участник, группа или вся организация) и с какой ролью имеет доступ к пространству, до какого уровня конфиденциальности | группа `acme/pmo` — `contributor` в `acme.pmo` до уровня 1 |
| **Уровень конфиденциальности** (`classification`) записи | 0 — открыто, 1 — внутреннее, 2 — конфиденциально, 3 — строго ограничено | бюджет проекта — 2, данные сотрудника — 3 |
| **Граница раскрытия** (`visibility`, уже есть, 04) | Где факт можно **произнести** агенту в чате (аудитория ответа). Не заменяет классификацию: классификация — кто может **прочитать** | `same_chat` |

Слои в типичной компании: **личный** (у каждого сотрудника) → **команда/проект** → **отдел** → **организация**. Каждый слой — отдельное пространство. Слой определяет, *чьё* это знание и кто его ведёт; классификация — *насколько* оно чувствительное внутри слоя.

## Роли в пространстве

| Роль | Права | Кто обычно |
|---|---|---|
| `reader` | `read` | смежные команды, наблюдатели |
| `contributor` | `read`, `write` (запись, доказательства, сигналы) | участники группы |
| `curator` | + `review` (подтверждения, разбор уборки, откат замещений), `forget` | руководитель/ответственный за знания группы |
| `owner` | + `manage` (гранты, настройки пространства) | владелец личного пространства; руководитель подразделения |

`admin` — не роль, а эксплуатационное право токена (только с localhost): миграции, выгрузка, стенд.

## Решение о доступе [DET]

Чистая функция `policy.resolve(principal, namespace) → (права, max_classification)`:

1. Организация участника = организация пространства, иначе — **нет доступа** (403, без подробностей).
2. Для агента берётся человек из `on_behalf_of`: считаются **его** гранты.
3. Гранты участника: прямые + через все группы, где он состоит (с учётом вложенности) + грант «вся организация». Итоговая роль — наибольшая; итоговый уровень — наибольший `max_classification` среди этих грантов, но не выше личного допуска участника (`principals.clearance`). Истёкшие гранты (`expires_at`) не считаются.
4. **Потолок токена**: права и пространства, записанные в токене, — верхняя граница. Эффективные права = права роли ∩ права токена. Так токен Claude Code может быть «только read/write в work», даже если владелец — `owner`.
5. Нет роли → 403 на всё пространство; есть роль → каждая запись дополнительно фильтруется `classification ≤ max_classification`.

**Фильтр — до ранжирования, в SQL** (как теги, R-3): запись выше допуска не участвует ни в поиске, ни в счётчиках, ни в `explain`, ни в `history`, ни в `stats`. Прямой `GET` такой записи → 404 (не 403 — не раскрываем существование).

Запись: `classification` новой записи — по умолчанию уровень пространства; писать можно не выше своего допуска (иначе 400). Понизить уровень записи может только `curator` (новая запись с `supersedes`, как любое изменение — D-1).

## Слои в поиске

`recall` сейчас работает в одном пространстве. Для корпоративного сценария добавляется **поиск по слоям** (этап 3+): `POST /v1/recall` с `layers: ["personal", "group:acme/pmo", "tenant"]` или без него — по всем доступным пространствам. Для каждого пространства применяется своя проверка из п. 1–5; в ответе у записи указан слой. Вес слоя в ранжировании — параметр (по умолчанию ближний слой чуть выше: личное > команда > отдел > организация).

## Перенос знания между слоями («продвижение»)

Личное знание может стать командным, командное — общим. Это **не копирование тихо**, а предложение куратору целевого слоя:

1. `POST /v1/{ns}/memories/{id}/promote {to: <namespace>}` — нужно право `write` в исходном и `write` в целевом.
2. В целевом пространстве создаётся `review_item: promotion` с текстом, доказательствами и предложенной классификацией.
3. Куратор принимает → в целевом слое новая запись (`source = promote:<ns>`, ссылка `promoted_from`), доказательства копируются; цитаты по выбору куратора — копируются или скрываются. Исходная запись не меняется.
4. Классификация при продвижении не понижается автоматически.

## Сон и LLM

- Лёгкий и глубокий сон работают **внутри одного пространства**; сравнение, сводки и дубли никогда не смешивают слои и организации.
- Сводка получает наибольшую классификацию из источников.
- Во внешний LLM (глубокий сон) не уходят записи с `classification = 3` и `visibility = owner_only` (S-6).
- Противоречие между слоями (личное говорит одно, командное — другое) сон не ищет; это станет возможным только при явном продвижении.

## Аудит и соответствие требованиям

| ID | Требование | Тип |
|---|---|---|
| AC-1 | В `audit_log` у каждого действия — участник и, для агента, от чьего имени | DET |
| AC-2 | Чтение записей уровня ≥ 2 пишется в `access_log`: кто, когда, id записей (без текста) | DET |
| AC-3 | Выдача и отзыв грантов, вступление в группы — в `audit_log` | DET |
| AC-4 | «Право на забвение»: владелец организации удаляет все записи о субъекте (`subject`) во всех пространствах организации одной операцией с `dry_run`/`confirm` | DET |
| AC-5 | Выгрузка пространства — только `owner` пространства или `admin`; выгрузка организации — только `admin` | DET |
| AC-6 | Изоляция организаций дублируется на уровне БД (Row Level Security по `tenant_id`) — этап перед подключением второй организации | DET |

## Модель данных (миграция 0002)

```text
tenants(id pk, name, created_at)
principals(id pk, tenant_id fk, kind user|agent|service, display_name,
           on_behalf_of fk principals null,       -- только для agent
           clearance smallint 0..3, active bool, created_at)
groups(id pk, tenant_id fk, parent_id fk groups null, name, kind org_unit|team|project|role)
group_members(group_id fk, principal_id fk, role member|curator, added_at, pk(group_id, principal_id))
namespaces + tenant_id fk, scope personal|group|tenant, owner_principal null, owner_group null,
             default_classification smallint, profile work|assistant (какие виды записей допустимы)
kinds.namespaces -> kinds.profiles
namespace_grants(id, namespace fk, subject_type principal|group|tenant, subject_id,
                 role reader|contributor|curator|owner, max_classification smallint,
                 granted_by, granted_at, expires_at null)
memories + classification smallint not null 0..3, promoted_from uuid null
clients (токены) + principal_id fk principals — права и пространства токена становятся «потолком»
audit_log + principal_id, on_behalf_of
access_log(id, at, principal_id, on_behalf_of, namespace, memory_ids uuid[])
review_items.type + 'promotion'
```

Миграции не создают ни организаций, ни участников, ни пространств. Первую организацию, человека, его личное пространство `<человек>.work` с грантом `owner` до уровня 3 и агента с токеном создаёт `python -m mem.cli init`. Служебный участник `admin` (организация `system`) появляется при запуске, если задан `MEM_ADMIN_TOKEN`.

## Критерии приёмки

- Член группы `acme/pmo/shop-team` читает пространство `acme.pmo` с грантом группе `acme/pmo` (наследование вверх по дереву); не член — 403.
- Агент от имени сотрудника без доступа к `acme.finance` получает 403, даже если в токене агента указан `acme.finance`.
- Запись уровня 2 не видна участнику с допуском 1 ни в `recall`, ни в `list`, ни в `stats`; прямой `GET` → 404.
- Участник организации `acme` не получает ничего из `demo` ни при каком запросе (403, одинаковый ответ для существующего и несуществующего пространства).
- Запись уровня выше собственного допуска → 400.
- Грант с истёкшим `expires_at` не даёт доступа.
- Все существующие тесты этапа 1 проходят без изменений в поведении.
