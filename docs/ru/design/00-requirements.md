# 00. Требования

[English](../../design/00-requirements.md) · **Русский**

## Назначение

Долговременная память для двух классов клиентов — личного агента-ассистента и AI-ассистентов разработки (Claude Code, Claude Desktop, Cursor) — с поиском по русскому и английскому тексту, явной историей изменений фактов, предсказуемым забыванием и настоящим удалением. Сервис хранит, находит, **ведёт жизненный цикл знаний** (сила, сон, замещение, забывание — 05) и выносит спорное человеку; извлекает факты из сырого текста клиент.

## Сценарии

- **M-S1. Claude Code наступил на граблю** → `remember(namespace=work, kind=gotcha, text="Shop: Next.js redirect через request.url уводит на localhost:3002…", tags=[project:shop, nextjs])`. Через неделю в новой сессии `recall("редирект next.js за nginx", tags=[project:shop])` возвращает запись первой.
- **M-S2. Cowork начинает работу над проектом** → скилл `project-context-boot` вызывает `recall` с тегом проекта и получает решения и грабли, отсортированные по свежести и типу.
- **M-S3. Агент записывает факт о человеке** → `remember(namespace=assistant, kind=person_fact, subject=person:petrov, text="Алексей Петров — подрядчик по бане, отвечает вечером")`.
- **M-S4. Факт изменился** → «Петров теперь подрядчик и по забору тоже» → `remember(..., slot=person:petrov#role)`. Слот занят — новая запись становится претендентом; сам Петров подтвердил в другом сообщении → ночью лёгкий сон заменяет старую (G1), в отчёте уборки — обе формулировки с цитатами. Если бы это сказал третий человек и никто не подтвердил — через 14 дней пункт «расхождение» в очереди.
- **M-S4a. Знание укрепляется** → о том, что Иванова отвечает только письменно, сказали трое в разных чатах → сила записи растёт; в брифинге и поиске она выше, чем факт, упомянутый однажды.
- **M-S5. Итог дня агента** → `remember(kind=episode, subject=chat:dacha, text="24.09: обсудили смету…")`. Через месяц глубокий сон сворачивает эпизоды месяца в сводку (если все даты и числа сводки есть в источниках — G2), эпизоды угасают и примерно через 3 месяца уходят в архив; факты о людях, которые подтверждаются и используются, — живут.
- **M-S6. «Забудь всё про Сидорова»** → агент вызывает `forget(subject=person:sidorov, mode=purge)`. Записи и векторы физически удалены, в аудите — только факт операции без текста.
- **M-S7. Воскресная уборка** → отчёт: что заменено (с цитатами), что забыто, что «протухло?», какие расхождения ждут решения. Агент показывает его в воскресном вечернем отчёте, я разбираю кнопками; в Cowork — инструментом `review_list`. Любая ошибка стадий → алерт в Telegram.
- **M-S9. Ответ с источником** → «Когда Чижову удобно созваниваться?» → «По утрам — со слов самого Чижова, чат «Гнездо», 22.09» (доказательство из `evidence`).
- **M-S8. Смотрю память глазами** → `list(namespace=work, tags=[project:shop])` из Cowork через MCP.

## Функциональные требования

| ID | Требование | Соавт. | Тип |
|---|---|---|---|
| F-1 | Запись сохраняет `text`, `kind`, `subject`, `tags`, `importance`, `source`, `occurred_at` ровно так, как прислал клиент | 4 | DET |
| F-2 | Пространства (`namespace`) изолированы: токен клиента разрешает список пространств; запрос к чужому → 403 | 4 | DET |
| F-3 | Гибридный поиск: вектор (локальная многоязычная модель) + полнотекстовый (Postgres FTS, словари `russian` и `english`) + фильтры по пространству, `kind`, `subject`, тегам (И / ИЛИ), времени; ранжирование по формуле из 04 | 4 | DET |
| F-4 | Замещение: явное (`supersedes`) или через слот и ворота G1; претенденты, спор, откат — 05 §2 | 4 | DET |
| F-5 | Забывание: архив по силе (ворота G3) и purge по правилам `retention_rules` или по явному запросу; каждое действие — строка в `audit_log` | 4 | DET |
| F-6 | `forget(mode=archive)` — скрыть из поиска с возможностью вернуть; `forget(mode=purge)` — физически удалить текст, вектор и связи | 4 | DET |
| F-7 | Лёгкий сон каждую ночь: затухание, продвижение претендентов, точные дубли, забывание по силе, правила хранения, проверка инвариантов; отчёт `OK` / `PARTIAL` / `FAILED` | 4 | DET |
| F-8 | Глубокий сон (уборка) раз в неделю: поиск противоречий, предложения слотов, «протухло?», сводки эпизодов; автоприменяются только сводки, прошедшие ворота G2, остальное — в очередь `review` | 2–3 | LLM+DET |
| F-12 | Каждая запись имеет ≥ 1 доказательство; доказательства добавляются к существующей записи и подкрепляют её | 4 | DET |
| F-13 | Сила записи считается по формулам 05 §1 и используется в ранжировании и забывании | 4 | DET |
| F-14 | `recall`/`list` с `audience` соблюдают `visibility` записей (04) | 4 | DET |
| F-9 | REST и MCP используют один слой бизнес-логики; каждая MCP-операция имеет REST-эквивалент | 4 | DET |
| F-10 | Экспорт пространства в JSONL и импорт из JSONL (бэкап, миграция) | 4 | DET |
| F-11 | Каждая запись получает эмбеддинг синхронно при записи (локальная модель); запись без эмбеддинга невозможна — ошибка возвращается клиенту | 4 | DET |

## Не цели (v1)

- Извлечение фактов из сырого текста (это делает клиент: агент — своим LLM, Claude Code — сам).
- Граф сущностей и автоматическое распознавание людей.
- Автоматическое слияние записей в одну (сводки глубокого сна **добавляются** поверх эпизодов, исходники не скрываются).
- Мультипользовательский SaaS, регистрация, веб-интерфейс (кроме `/status`).

## Критерии приёмки (сводно, детально — в 07)

- Все 42 канарейки из проверки прежнего сервиса памяти, перенесённые в формат mem, дают предсказуемый исход: вид не меняется, три разные сметы не сливаются, перенос встречи подтверждённым автором — замещение (G1), без подтверждения — расхождение в очереди, сила после 60 смоделированных ночей не выравнивается, забывание — только по воротам G3, purge — без остатка.
- Recall@10 на наборе из 20 пар «запись — вопрос другими словами» (русский) ≥ 0,8.
- Отчёт ночной задачи при искусственно сломанной стадии = `FAILED` и алерт.
