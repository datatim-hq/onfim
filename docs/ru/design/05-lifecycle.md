# 05. Жизненный цикл: сила памяти, сон, замещение, забывание

[English](../../design/05-lifecycle.md) · **Русский**

## Назначение

Реализовать то, чего мы ждали от прежнего сервиса памяти и не получили: **циклы сна, ранжирование знаний по силе, замещение старых суждений подтверждёнными новыми и забывание**. Отличие — в трёх гарантиях:

1. **Всё, что меняется автоматически, меняется по формуле или правилу из этого документа** и покрыто тестом; LLM только предлагает, применяются предложения через проверяемые «ворота» (gates).
2. **Каждое изменение обратимо** в течение окна хранения и **подкреплено доказательством** (цитата, источник, дата).
3. **Спорное уходит человеку** (очередь `review_items`), а не решается молча.

## Состояния записи

```text
                 remember (слот свободен / без слота)
    ────────────────────────────────────────► current ◄──── promote (ворота G1) ────┐
                                               │   ▲                                 │
    remember в занятый слот ─────────────────► candidate ── нет подтверждения 30 дн ─┤
                                               │   │                                 ▼
                     supersede (явно/G1) ──────┘   └──► superseded (история, valid_to)
                                               │
                     сила < порога (G3) ───────┴──► archived ── правило purge ──► (строки нет)
                                                        │  ▲
                                             unarchive  └──┘
```

## 1. Сила памяти (ранжирование знаний)

У каждой записи есть **сила** `s ∈ [0,1]` — насколько знание живо: подтверждено ли разными источниками, используется ли, давно ли о нём было слышно. Сила — основа ранжирования в поиске (04) и забывания (§4). Это не то же, что `importance`: важность задаёт клиент один раз при записи, сила меняется со временем.

### Начальная сила [DET]

`s₀ = {1: 0.35, 2: 0.55, 3: 0.75}[importance] + 0.10`, если первое доказательство от владельца (`speaker = owner`); не выше 0,90.

### Затухание [DET]

`s(t) = s(t₀) · 2^(−(t − t₀) / H)`, где `H` — период полураспада вида (02). Не затухают: виды без `H`, `pinned`, открытые `commitment_mirror`. Затухание считается лениво (при чтении) и фиксируется лёгким сном. **Пересчёт никогда не повышает силу** (D-6) — прямой урок прежнего сервиса, где «пол 0,35» поднимал всё до одного значения.

### Подкрепление [DET]

Каждое событие: `s ← s + w · (1 − s)` (насыщение к 1, без перескока).

| Событие | w | Замечание |
|---|---|---|
| Новое **независимое** доказательство (новый `independent_key`: другой говорящий или другой источник) | 0,30 | Главный путь «подтверждения» |
| Повтор от того же источника | 0,05 | Повтор ≠ подтверждение |
| Подтверждение владельцем (`owner_confirm`) | 0,50 | Кнопка в боте / инструмент MCP |
| Запись реально использована клиентом (`used`) | 0,15 | Агент процитировал в брифинге/ответе |
| Отмечена полезной (`helpful`) | 0,25 | |
| Попала в топ-5 выдачи (`recalled_top5`) | 0,03 | Не чаще 1 раза в сутки на запись |
| Эпизод вошёл в сводку глубокого сна (`summarized_into`) | `s ← s · 0,5` | Знание перешло в сводку, эпизод угасает быстрее |

### Примеры (для тестов и интуиции)

| Запись | Без подкреплений упадёт ниже порога забывания 0,08 через |
|---|---|
| `episode`, importance 2 | ≈ 83 дня |
| `note`, importance 2 | ≈ 250 дней |
| `insight`, importance 2 | ≈ 335 дней |
| `person_fact`, importance 2, два независимых источника (s ≈ 0,69) | ≈ 3 года |
| `person_fact`, упомянутый владельцем и используемый в брифингах раз в месяц | не упадёт |

## 2. Замещение: старое суждение → подтверждённое новое

### Явное замещение

Клиент передаёт `supersedes = <id>` (он уверен: «встреча перенесена»). В одной транзакции старая запись → `superseded`, `valid_to = now()`; новая → `current`. Это и есть подтверждение — клиент за него отвечает.

### Замещение через слот и подтверждение

Новая запись в занятый слот без `supersedes` становится **претендентом** (`candidate`). Текущая остаётся действующей, пока претендент не подтверждён.

**Повтор того же утверждения** (с 08.10): запись в занятый слот с тем же видом, субъектом, видимостью и грифом и тем же текстом (без учёта регистра, ё/е, пробелов, точки в конце), что у действующей записи, — не претендент, а подтверждение: доказательство добавляется к действующей записи (подкрепление, как `add_evidence`), ответ — эта запись с `reinforced: true`. Иначе ночью дубль заменял бы оригинал (тот же говорящий, G1b) и подкрепление пропадало. Только для действующей записи и только если в слоте нет претендента (подкрепление меняет ворота G1); не для правил (`decision`, `convention`, `gotcha` — у них своя очередь подтверждения), не при `supersedes`, `external_ref` и переносе между слоями; `same_chat` — только из того же чата, где уже есть доказательство (круг показа не расширяется); запоздалое старое (`occurred_at` раньше записи) идёт обычным путём — в историю.

**Ворота G1 — продвижение претендента** (лёгкий сон, детерминированно). Претендент C заменяет текущую K, если выполнены все условия:

| # | Условие |
|---|---|
| a | C новее: `C.occurred_at ≥ K.occurred_at` (при отсутствии — `created_at`) |
| b | C подтверждён — хотя бы одно из: доказательство от владельца; ≥ 2 независимых доказательства; тот же говорящий, от которого было исходное доказательство K (человек сам изменил своё утверждение: «давай не в чт, а в пт») |
| c | После первого доказательства C не появилось новых доказательств в пользу K |

Если C старше K (запоздалое сообщение, импорт) — C сразу записывается в историю как `superseded` с `valid_to = K.valid_from`.

Если C не прошёл G1 за 14 дней — создаётся `review_item` типа `contradiction` с цитатами обеих сторон. Нет решения за 30 дней → C архивируется, пункт очереди — `expired`.

Пока идёт спор, `recall` отдаёт текущую запись с пометкой `contested: true` и id претендента — клиент видит, что есть непроверенное обновление.

**Откат:** `revert_supersede(<id>)` в течение 30 дней возвращает прежнюю запись в `current`, новую — в `candidate`. Всё в `audit_log`.

### Противоречия без слотов

Записи без слота сервис сравнивать не может — это задача глубокого сна (§3): LLM ищет противоречия внутри одного `subject` и **создаёт `review_item`** с цитатами. Сам ничего не заменяет. Если противоречие — про один атрибут, в предложении есть слот: принятие проставляет слот обеим записям, дальше работают ворота G1.

## 3. Циклы сна

### Лёгкий сон — каждую ночь, 03:30 [DET]

| Стадия | Что делает |
|---|---|
| `decay` | Фиксирует затухание силы всех записей (`strength`, `strength_at`) |
| `dedup_exact` | Точные дубли (нормализованный текст: регистр, пробелы, `ё→е`) в пределах `namespace + kind + subject + гриф + видимость + слот`: доказательства переносятся в оставляемую запись — действующую, иначе старшую (это подкрепление), дубль получает `duplicate_of` и скрывается. Записи `same_chat` склеиваются, только если у них один набор чатов доказательств (иначе расширился бы круг показа). С 08.10 идёт до `promote`: дубль-претендент того же текста не заменяет оригинал |
| `promote` | Ворота G1 для всех претендентов; просроченные претенденты → очередь / архив |
| `forget` | Ворота G3 (§4) |
| `retention` | Правила `retention_rules` (purge архива, история замещений) |
| `review_expiry` | Закрывает просроченные пункты очереди |
| `maintenance` | `ANALYZE`, проверка инвариантов D-1…D-8 |
| `export` | JSONL-экспорт пространств в бэкап |

### Глубокий сон («уборка») — раз в неделю, воскресенье 04:00

Использует LLM (Claude через Anthropic API — тот же обработчик, что уже видит сообщения у агента; эмбеддинги остаются локальными). Все стадии, кроме G2, **только создают предложения**.

| Стадия | Что делает | Применяется |
|---|---|---|
| `contradictions` | По каждому `subject` с ≥ 2 текущими записями без общего слота: LLM ищет пары, которые не могут быть верны одновременно; ответ — пара, объяснение, цитаты из `evidence` | `review_item: contradiction` |
| `slot_suggestions` | Предлагает слот записям, которые описывают один атрибут (кроме `episode`, `commitment_mirror`, `insight` — это события и сводки, а не меняющиеся атрибуты) | `review_item: slot_suggestion` |
| `stale` | Записи вида с `review_below` (gotcha) при силе ниже порога и записи, на которые ссылаются события «не сработало» | `review_item: stale` («протухло?») |
| `summaries` | Эпизоды одного `subject` старше 30 дней, сгруппированные по месяцу → сводка `topic_fact`/`insight` | **Автоматически, если прошли ворота G2**, иначе `review_item: merge_suggestion` |
| `report` | Отчёт уборки (ниже) | — |

**Ворота G2 — автоприменение сводки** (детерминированная проверка результата LLM):

| # | Условие |
|---|---|
| a | Все числа, даты и время в сводке встречаются хотя бы в одном источнике (регулярное извлечение, нормализация форматов дат) — **урок прежнего сервиса: «30.09» не может стать «до 1 октября»** |
| b | Все имена собственные в сводке (слова с заглавной буквы, кроме начала предложения) есть в источниках (нормализация `ё→е`, падеж — по основе) |
| c | Сводка не длиннее суммарного текста источников |
| d | Источники — только `episode`; `commitment_mirror`, `decision`, `convention`, `person_fact` никогда не сворачиваются |
| e | Язык сводки = язык источников |

Прошла — создаётся запись (`source = sleep:deep`, доказательства = объединение доказательств источников), источникам — событие `summarized_into`. Источники не скрываются, просто быстрее угасают.

### Отчёт уборки

`GET /v1/{ns}/sleep/latest` — для человека и для брифинга агента:
- **Замещено** (старое → новое), по каждому: обе формулировки, основание (G1a/b/c), цитаты.
- **Забыто** (ушло в архив по силе): число по видам + 10 примеров.
- **Протухло?** — пункты `stale` с цитатой последнего доказательства.
- **Расхождения** — открытые `contradiction` с цитатами обеих сторон.
- **Сводки** — созданные и отклонённые G2 (с причиной).
- Статус стадий и ошибки.

### Честность отчёта [DET]

Статус задачи вычисляется из ошибок стадий: все без ошибок → `OK`; ошибка в `contradictions`, `slot_suggestions`, `stale`, `summaries`, `dedup_exact`, `review_expiry`, `export` → `PARTIAL`; ошибка в `decay`, `promote`, `forget`, `retention`, `maintenance` → `FAILED`. `PARTIAL`/`FAILED` → алерт в Telegram. Повторный прогон на тех же данных ничего не меняет (идемпотентность). `dry_run` возвращает те же счётчики, ничего не меняя.

## 4. Забывание

**Ворота G3 — архив по силе** (лёгкий сон). Запись уходит в архив, если все условия:

| # | Условие |
|---|---|
| a | Вид `forgettable` |
| b | Не `pinned` |
| c | Сила после затухания < 0,08 |
| d | Нет событий `used`/`helpful` за последние 30 дней |
| e | Не `current` в слоте, у которого есть открытый `review_item` |

Архив обратим (`unarchive` ставит силу 0,30 и отметку события). В отчёте уборки — счётчики и примеры.

**Правила purge** (`retention_rules`):

| id | namespace | kind | условие | дней | действие |
|---|---|---|---|---|---|
| r-assistant-purge | assistant | * | archived_older_than | 365 | purge |
| r-history-archive | * | * | superseded_older_than | 180 | archive (история остаётся в `history` до purge) |

В пространстве `work` автоматического purge нет.

**Явное забывание:** `forget(mode=archive|purge)` — одна запись или массово по фильтру с `dry_run` и `confirm=<N>` (03).

## Функциональные требования

| ID | Требование | Соавт. | Тип |
|---|---|---|---|
| L-1 | Все переходы состояний — функции `mem.lifecycle`, каждая пишет `audit_log` в той же транзакции | 4 | DET |
| L-2 | Формулы силы, пороги и веса — константы в `mem/config/lifecycle.py`, покрыты property-тестами; изменение без обновления тестов валит CI | 4 | DET |
| L-3 | Ворота G1, G2, G3 — чистые функции с таблицами тест-кейсов | 4 | DET |
| L-4 | LLM-стадии глубокого сна получают только тексты записей и цитаты одного `subject`, ответ — строго по JSON-схеме; невалидный ответ → ошибка стадии (`PARTIAL`), а не «пустое предложение» | 3 | LLM+DET |
| L-5 | Каждое автоматическое изменение обратимо не менее 30 дней (архив, `revert_supersede`) | 4 | DET |
| L-6 | Правило или стадию можно выключить без деплоя; выключенное видно в отчёте как `disabled` | 4 | DET |

**Модель для сна (с 08.10).** Модели — настройки `MEM_DEEP_MODEL_REASON` и
`MEM_DEEP_MODEL_SUMMARY`, маршрут — приставка в имени (`mem/llm.py`, `RoutedLLM`): без приставки или `anthropic:` —
Anthropic; `openai:<модель>` — модель внутри контура по протоколу, совместимому с OpenAI (`MEM_OPENAI_BASE_URL`,
`MEM_OPENAI_API_KEY`), только из списка `MEM_OPENAI_IN_CONTOUR_MODELS`. Облачные маршруты (`yandex:`, `gigachat:`,
`openai:` вне списка) для сна не поддержаны: словаря меток у mem нет, записи ушли бы без маскирования. Такая настройка
— ошибка до первого вызова: стадии с моделью завершаются ошибкой (`PARTIAL` с алертом), ничего не отправляется.
Модели по умолчанию нет: стадия, чья модель не задана, выключена (`DISABLED` в отчёте, без алерта и без обращения к
модели), даже если ключ Anthropic лежит в настройках. Anthropic — только явно, например
`MEM_DEEP_MODEL_REASON=claude-sonnet-5`, `MEM_DEEP_MODEL_SUMMARY=claude-haiku-4-5-20251001`.

## Критерии приёмки (детально — 07)

- **Сила не выравнивается:** 42 канарейки после 60 смоделированных ночей имеют разброс силы (стандартное отклонение ≥ 0,1), порядок по силе совпадает с порядком по числу независимых подтверждений.
- **Замещение с подтверждением:** «созвон чт 15:00» (Чижов) → «пт 16:00» от того же Чижова → лёгкий сон продвигает претендента (G1b); от третьего лица без подтверждения → через 14 дней `review_item` с двумя цитатами.
- **Разное не сливается:** три сметы и чертёж одному человеку остаются четырьмя текущими записями; глубокий сон не сворачивает их (G2d, вид `commitment_mirror`).
- **G2 ловит искажение:** сводка, где дата источника «30.09» превращена в «1 октября», отклоняется с причиной `a`.
- **Забывание по силе:** эпизод без подкреплений архивируется примерно через 83 дня (моделирование времени), `decision` того же возраста — нет, `person_fact`, использованный в брифинге 20 дней назад, — нет.
- **Честный отчёт:** ошибка в `contradictions` → `PARTIAL` + алерт; в `promote` → `FAILED`.
