# 09. Память команды: общий слой, личные слои, делегирование

[English](../../design/09-team-memory.md) · **Русский**

> v0.1, 02.10.2026. Развивает модель доступа (08) до рабочего командного сценария. Решения владельца 02.10: строим полноценную командную работу, проверяем на вымышленном отделе продаж (организация `globex` в `tests/integration/test_team.py`).

## Назначение

Команда пользуется одним агентом. У команды есть общая память, у каждого участника — личная. Агент, отвечая человеку, видит ровно то, что вправе видеть этот человек. В общую память попадает только сказанное в командных чатах и то, чем человек поделился сам.

Модель доступа (08) уже даёт организации, группы, роли, уровни конфиденциальности и поиск по слоям. Эта спека добавляет недостающее: делегирование сервису агента, автора реплики как участника, доверие в команде, перенос между слоями, маршрут очереди решений, уход участника и внешний ключ сущности для CRM.

## Понятия

| Понятие | Что это | Пример |
|---|---|---|
| **Команда** | Группа (`group`) с командным пространством (`scope = group`, профиль `team`) | группа `gx/sales`, пространство `gx.sales` |
| **Личный слой** | Личное пространство участника (`scope = personal`, профиль `assistant`) | `gx.u.bob` |
| **Куратор** | Участник с ролью `curator` в командном пространстве: решает по очереди команды | руководитель отдела |
| **Делегированный клиент** | Служебный токен агента команды. Сам доступа к записям не имеет; действует от имени участника группы или от имени самой группы | клиент `gx-agent` с делегированием на `gx/sales` |
| **Автор реплики** | Участник организации, чьи слова стали доказательством (`evidence.speaker_principal`) | `bob` |
| **Внешний собеседник** | Тот, кто пишет в чате, но не состоит в организации: клиент, представитель поставщика | — |

## Сценарии

- **TM-S1. Вопрос в личном чате с агентом.** Агент вызывает поиск по слоям от имени сотрудника: личный слой и слой команды, личное весит чуть больше.
- **TM-S2. Вопрос в командном чате.** Агент вызывает поиск от имени **группы**. Личных слоёв в выдаче нет по построению: у группы нет на них грантов.
- **TM-S3. «Поделиться с командой».** Сотрудник отправляет личную запись в командный слой. Куратор получает предложение с текстом и доказательствами и принимает или отклоняет. Исходная запись не меняется.
- **TM-S4. Два независимых подтверждения.** Двое менеджеров в разное время сообщают одно и то же об объекте. Это два независимых источника: претендент замещает устаревшую запись лёгким сном (ворота G1, 05).
- **TM-S5. Правило команды.** Участник пишет в командном чате «бронь держим не дольше трёх дней». Запись вида «регламент» становится претендентом и ждёт куратора. Если это сказал куратор — действует сразу.
- **TM-S6. Внешний собеседник.** Представитель поставщика пишет в смешанном чате «цены на третий корпус вырастут с 10 октября». Запись сохраняется как недоверенная: агент подаёт её «по словам …», правилом она не становится.
- **TM-S7. Руководитель и личное.** Куратор запрашивает личное пространство сотрудника — отказ 403, как для несуществующего пространства.
- **TM-S8. Расхождение в команде.** Двое участников утверждают разное в одном слоте. Пункт «расхождение» с обеими цитатами уходит куратору.
- **TM-S9. Уход участника.** Участник отключён: все его токены и делегирование от его имени перестают работать; личный слой выгружается ему и стирается; его реплики в памяти команды остаются доказательствами.
- **TM-S10. Сведения из CRM.** Запись о сделке хранится с внешним ключом `crm:deal:…`; поиск по человеку из чата находит и её, если человек связан с контактом CRM.

## Функциональные требования

### Делегирование

| ID | Требование | Тип |
|---|---|---|
| TM-1 | У клиента появляется необязательное поле `delegate_group`. Такой клиент обязан указывать в каждом запросе, от чьего имени действует: заголовок `X-Mem-On-Behalf-Of` со значением `<participant_id>` или `group:<group_id>`. Без заголовка — 400 | DET |
| TM-2 | От имени участника можно действовать, только если он активен и состоит в `delegate_group` или её дочерней группе. Иначе — 403 | DET |
| TM-3 | Права запроса = права этого участника (08, шаги 1–5) ∩ потолок токена. Делегированный клиент не получает ничего сверх прав человека | DET |
| TM-4 | От имени группы (`group:<id>`) учитываются только гранты самой группы, её родительских групп и гранты «вся организация». Личные пространства недоступны по построению | DET |
| TM-5 | В `audit_log` и `access_log` пишутся клиент и тот, от чьего имени он действовал (AC-1) | DET |
| TM-6 | Через MCP делегирование не используется: у MCP-клиента один человек на токен, как сейчас | DET |

### Автор реплики и доверие

| ID | Требование | Тип |
|---|---|---|
| TM-7 | Доказательство получает необязательное поле `speaker_principal`. Участник должен существовать в организации пространства, иначе 400. Поле `speaker` остаётся для показа | DET |
| TM-8 | Ключ независимости доказательства: `p:<speaker_principal>`, если автор указан; иначе прежнее правило (`кто сказал@источник`). Пересланное по-прежнему считается одним источником (1.6) | DET |
| TM-9 | **Доверие в личном слое** — как сейчас: слова владельца слоя и собственная работа доверенного клиента. Владелец определяется так: `speaker_principal` равен владельцу пространства либо `speaker = owner` | DET |
| TM-10 | **Доверие в командном слое:** доверенное доказательство — от участника группы-владельца. От внешнего собеседника и из внешних источников — недоверенное | DET |
| TM-11 | **Правила команды** (виды `decision`, `convention`) в командном слое действуют сразу, только если автор — куратор. От остальных участников запись становится претендентом, куратору создаётся пункт `rule_confirm` | DET |
| TM-12 | Профиль пространства `team` допускает виды: `topic_fact`, `person_fact`, `insight`, `episode`, `commitment_mirror`, `decision`, `convention`, `crm_mirror` | DET |

### Перенос между слоями

| ID | Требование | Тип |
|---|---|---|
| TM-13 | `POST /v1/{ns}/memories/{id}/promote` с телом `{to, share_quotes?, note?}`. Нужно право `write` в исходном и в целевом пространстве. Оба — в одной организации | DET |
| TM-14 | В целевом пространстве создаётся пункт очереди `promotion`: текст, вид, тема, слот, доказательства, предложивший, предложенный уровень конфиденциальности. При `share_quotes = false` цитаты в пункт не попадают | DET |
| TM-15 | Куратор принимает → в целевом слое создаётся новая запись: `source = promote:<исходное пространство>`, `promoted_from = <id>`, доказательства копируются с прежними ключами независимости. Если слот занят, запись становится претендентом по обычным правилам (05) | DET |
| TM-16 | Куратор отклоняет → в целевом слое ничего не появляется. Исходная запись не меняется ни в одном из исходов | DET |
| TM-17 | Уровень конфиденциальности при переносе автоматически не понижается (08) | DET |
| TM-18 | Повторный перенос той же записи в то же пространство при открытом пункте — 409. После отклонения повтор возможен | DET |
| TM-19 | Настройка пространства `promotion_auto`: список видов, которые принимаются без куратора. По умолчанию пусто | DET |

### Очередь решений в команде

| ID | Требование | Тип |
|---|---|---|
| TM-20 | Пункты очереди командного пространства видят и решают участники с правом `review` в нём, то есть кураторы. Пункты личного пространства — только его владелец | DET |
| TM-21 | `GET /v1/review` без пространства возвращает открытые пункты по всем пространствам, где у вызывающего есть право `review`, с указанием слоя | DET |
| TM-22 | В пункте `promotion` и `rule_confirm` указан предложивший (`proposed_by`) | DET |

### Поиск по слоям

| ID | Требование | Тип |
|---|---|---|
| TM-23 | Поиск по слоям (`recall_layers`) принимает `scopes`: подмножество `personal`, `group`, `tenant`. Без него — все доступные | DET |
| TM-24 | Для ответа в командном чате клиент обязан вызывать поиск от имени группы (TM-4). Параметр `scopes` — удобство, а не защита | DET |
| TM-25 | У каждой записи в ответе указан слой: пространство и его тип (уже есть) | DET |

### Уход участника и «забыть субъекта»

| ID | Требование | Тип |
|---|---|---|
| TM-26 | `offboard <participant>`: участник становится неактивным, его клиенты отзываются, он выводится из групп. С этого момента любое обращение от его имени — 403 | DET |
| TM-27 | Личный слой ушедшего: выгрузка (право владельца или `admin`), затем удаление по сроку — по умолчанию через 30 дней, можно сразу. До удаления слой никому не доступен | DET |
| TM-28 | Реплики ушедшего в памяти команды остаются доказательствами с его именем. Его записи-претенденты в очереди куратора остаются | DET |
| TM-29 | «Забыть субъекта»: операция уровня организации удаляет все записи с данным `subject` и его псевдонимами во всех пространствах организации. Режимы `dry_run` и `confirm = <число записей>`, как в `forget` (03). Право — владелец организации или `admin` | DET |

### Внешний ключ сущности

| ID | Требование | Тип |
|---|---|---|
| TM-30 | Тема записи (`subject`) может быть внешним ключом: `crm:contact:<id>`, `crm:deal:<id>`, `crm:object:<id>` | DET |
| TM-31 | Таблица псевдонимов темы на организацию: `person:tg123 → crm:contact:77`. Фильтр по `subject` в поиске и списке учитывает псевдонимы в обе стороны | DET |
| TM-32 | Вид `crm_mirror`: запись-зеркало сущности CRM с `external_ref`. Пока сущность открыта, сила не затухает; после закрытия (`/close`) затухает и забывается, как `commitment_mirror` | DET |
| TM-33 | Доказательство с `source_scope = crm` недоверенным не считается, но и независимым подтверждением чатам не служит, если сама запись в CRM создана агентом (ключ независимости `crm:<сущность>` один на сущность) | DET |

### Сон

| ID | Требование | Тип |
|---|---|---|
| TM-34 | Лёгкий и глубокий сон по-прежнему идут внутри одного пространства и слои не смешивают (08) | DET |
| TM-35 | Глубокий сон личных пространств разносится по времени; настройка пространства `deep_sleep: weekly | off` | DET |

## Модель данных (миграция 0005)

```text
clients         + delegate_group text null → groups(id)
evidence        + speaker_principal text null → principals(id)
namespaces      + settings jsonb not null default '{}'     -- promotion_auto, deep_sleep
kinds             профиль team; новый вид crm_mirror (полураспад как у commitment_mirror)
review_items    + proposed_by text null → principals(id)
subject_aliases   (tenant_id, alias, canonical, created_by, created_at; pk (tenant_id, alias))
```

Существующие клиенты и записи не меняются: все новые поля необязательные, поведение без них прежнее.

## Критерии приёмки

Матрица изоляции — на организации `globex` (пятеро участников, группа `gx/sales`, куратор):

- Сотрудник A через делегированный клиент читает свой личный слой и слой команды; личный слой B — 403.
- Куратор читает слой команды и решает по его очереди; личный слой любого сотрудника — 403.
- Запрос от имени `group:gx/sales` возвращает только слой команды, даже если в запросе названо личное пространство (403).
- Делегированный клиент без заголовка — 400; от имени участника чужой группы или чужой организации — 403; от имени неактивного — 403.
- Перенос: принят → запись в слое команды с `promoted_from`; отклонён → записи нет; исходная запись в обоих случаях не изменилась; повтор при открытом пункте — 409.
- Два доказательства от разных участников дают два независимых источника; два от одного участника в разных чатах — один.
- Регламент от участника — претендент и пункт `rule_confirm`; от куратора — действует сразу.
- Реплика внешнего собеседника в командном слое — `trust = untrusted`.
- После `offboard` обращение от имени ушедшего — 403; его реплики в слое команды видны.
- Поиск по `subject = person:tg123` находит запись с темой `crm:contact:77` при наличии псевдонима.
- Все прежние тесты проходят без изменений.
